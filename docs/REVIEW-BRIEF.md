你是一名资深 macOS 产品设计师 + 前端架构审阅者。下面这个项目需要你做**只读审阅**，
不许改动任何文件、不许给代码补丁，只输出诊断结论和 UX/UI 结构。

### 2.1 项目是什么

一个 macOS 桌面浮窗，宽度约 340 点，常驻最上层。用户每天给自己派活，干完勾掉。
它不是任务管理器，是一本**日账本**：一天一页，四个动作（记 / 划 / 结 / 稽），
记录"你欠了自己多少、欠了几天"。数据只在本地一个 JSON 里，除天气外不联网。

技术形态：Swift 壳（AppKit + WKWebView，3269 行）+ 前端（3789 行 JS / 924 行 CSS，
拼成单个 IIFE，10 个分片）+ 6 类边界审计 + 118 条行为断言。

### 2.2 必读，按这个顺序（不要跳）

1. `docs/MANUAL.md` —— **最重要**。这是使用者实际看到的每一处界面、每一个菜单项、
   每一种异常处理。你的 UX 诊断必须以它为准，而不是以代码推测。
2. `docs/POSITIONING.md` —— 定位与"新功能准入标准"（四个动作）。
3. `docs/AUDIT-2026-11-06.md` —— 已经做过的对抗性诊断，**已修的和未修的都在里面**。
   你不需要重复报告它已经列出的问题。
4. `docs/DEVELOPMENT.md` 第 1、2、3、4、5 节 —— 结构、启动链路、桥协议、数据格式、统计口径。
5. `src/index.html` + `src/styles.css`（按需查具体样式）+ `src/js/0*.js`（按需）。
6. `README.md`、`CONTRIBUTING.md` 的「不可加清单」。

### 2.3 三条硬约束（越界即无效）

违反任意一条的建议全部作废，不要写进来：

1. **不许建议任何形式的联网、账号、云同步、埋点、崩溃上报、运行时调用模型。**
   这些是这个产品的存在前提，不是待优化项。
2. **不许建议新增系统权限**（相机、麦克风、位置、辅助功能、输入监控、通讯录等）。
   现在只有日历、提醒事项（只读）和可选的完全磁盘访问。`Info.plist` 多一个键，
   CI 直接失败。
3. **不许建议自动更新机制。** 那会开一个"后台静默出网"的口子，
   与"用户可以用 `lsof` 验证它不联网"直接冲突。

另外：这个产品**明确不做**连续天数激励、番茄钟/专注计时、优先级、标签、看板、
AI 拆解任务、自动补记。理由在 `CONTRIBUTING.md`。你可以论证这些决定是错的，
但必须正面反驳理由，不能只说"主流产品都有"。

### 2.4 你要产出的东西（严格按这七节，不要写散文）

**第 1 节｜信息架构**
用一棵树列出：窗口的全部区域 → 每个区域里的元素 → 每个元素通向哪里。
标注每个区域**在什么条件下才出现**（例如"欠账条：存在 carried ≥ 2 的未完成任务时"）。
必须覆盖 MANUAL 第 4 节的全部内容，不许遗漏收起态。

**第 2 节｜屏幕与状态清单**
一张表，每行是一个"用户能看到的画面状态"：

| 状态 ID | 触发条件 | 画面上有什么 | 用户此刻最可能的意图 | 这个意图有没有出口 |

至少覆盖：首次打开（空白）、有 1 件、全部完成、有欠账、已收起为圆点、
提醒正在响、报告卡五个页签、数据读不出来、授权被拒、保存失败、离线（天气停更）。

**第 3 节｜交互路径图**
用文字箭头画出 5 条主路径，每条标出**步数**和**可能的断点**：

1. 想到一件事 → 写下来
2. 干完 → 勾掉
3. 打开看今天还剩几件
4. 发现自己拖了很久 → 处理掉（放回今天 / 认赔）
5. 觉得某个数字不对 → 纠正它

断点指的是：用户在这条路上可能不知道下一步做什么、或者以为做了但其实没生效的地方。

**第 4 节｜组件清单**
按"复用单位"列出界面组件（不是一个页面一个组件），每个给：
名称、出现位置、包含的元素、有哪几种视觉状态、点击区域尺寸是否够（≥ 28×28 点）。

**第 5 节｜视觉规范现状评估**
从 `src/styles.css` 读出实际的：字号阶梯（有几档、分别用在哪）、颜色变量、
圆角、间距节奏。然后指出：哪些地方**破坏了已有节奏**、哪些字号低于 10px 而承担了
必须读的信息、哪些可点元素没有 hover/active 反馈。

**第 6 节｜UX 缺陷清单（按严重度排序）**
每条格式固定：

```
[严重度 P0/P1/P2] 一句话结论
现象：在哪个状态、看到什么
为什么是问题：用户会误解成什么 / 会放弃哪一步
证据：MANUAL 第几节 / 代码哪个文件哪个函数
建议：改什么（只描述目标状态，不给代码）
```

**已经修过或已知的不要重复报告**（见 AUDIT 第 1–5 节）：
60 天后取消勾选不退账、carried 上界不一致、认赔不算观测、报告高度抖动、
"记得不牢"的假承诺、月级投票入口太深、`byId` 的 O(n²)、渲染函数里写盘。

**第 7 节｜优先级建议**
把第 6 节的结论压成"如果只改三件事，改哪三件"，每条说明它影响哪个动作
（记 / 划 / 结 / 稽）。如果某条改进会破坏定位，明确写出来。

### 2.5 评判标准（你的建议会按这个被筛）

这个产品有一条判断线，写在 `POSITIONING.md`：

> **这一栏能不能被用户反驳？**

所以：

- 加分：让用户**更快看清自己记的到底是什么**、让某个数字**更容易被核对**、
  让某个动作**少一步**。
- 减分：增加"用户无法反驳的数字"（专注时长、效率评分、健康分数）、
  增加需要解释才能懂的机制、把浮窗变重（多一层入口、多一个必须读的说明）。
- 直接作废：要求联网、要求权限、要求账号、要求自动更新。

## 3. 为什么这份任务书这么写

留给仓库维护者看的，不用发给审阅者。

- **先给 MANUAL 而不是代码**：代码会诱导审阅者去挑实现毛病，
  而这个产品最可能出问题的地方是"用户看不懂 / 看不见 / 以为生效了但没生效"。
- **禁掉三条硬约束**：外部审阅者最自然的建议就是"加同步""加自动更新""加个 AI 拆任务"，
  这三条会把这个产品拆掉。不提前写死，会浪费一整轮。
- **固定七节格式**：不限定结构的话，输出会是散文式评论，
  没法转成可执行的改动清单。
- **列出已知问题**：不然它会花一半篇幅重复 AUDIT 里已经修完的东西。
- **要求指出证据位置**：这是唯一能防"听起来很对但和实际界面不符"的办法。
