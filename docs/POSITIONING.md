# 定位：它是一本日账本，不是一个待办清单

> 日期 2026-11-06。命名暂时搁置，品类先定。
> 这份文档只解决一个问题：**以后每想加一个功能，用哪句话判断它该不该加。**

---

## 0. 一句话

**它不催你多干，只帮你记准。**

展开：

> 你每天给自己派活。它把这一天记成一页账：派了几件、划掉几件、哪几件滚到了明天。
> 一天结一次，一年下来是一本可以带走的账。

产品名（浮窗待办 / 年轮 / …）是**工作名**，随时可换。**品类词**是「日账本」。品类定了，名字的候选范围会自己收窄。

---

## 1. 为什么「待办」这个词不够

「待办」描述的是**数据结构**（一列还没做完的事），不是**产品**。

按这个词做下去，必然滑向：无限列表 → 优先级 → 标签 → 看板 → 协作 → 同步。
每一步都合理，加起来就成了另一个 Things / 滴答清单，而那个赛道已经有答案了。

回头看代码里的实际机制（读出来的，不是设想）：

- `data.json` 里最核心的结构是 **`daily` 账本**，键是日期；
- 所有统计先过 `dayObserved(day)`，区分「不知道」和「是零」；
- 有一整片代码（`07-truth.js`）专门让用户**反驳我记的数**；
- `due` 每天被 rollover 重写，所以它**不能进任何历史统计**；
- `carried` 记的是「这笔账顺延了几天」。

这些不是待办清单的机制，是**账本**的机制。产品早就是账本了，只是名字还叫待办。

---

## 2. 抽象：一天一页

三层，从下往上：

| 层 | 内容 | 落在哪 |
|---|---|---|
| **账期** | 唯一时间单位是**天**。跨天就结账，不跨天不算 | `daily[YYYY-MM-DD]` |
| **动作** | 记 · 划 · 结 · 稽，四个动作覆盖全部交互 | 见下表 |
| **意义** | 你在跟昨天的自己结算，不是在跟一个列表较劲 | 年轮 / 年报 / 报告卡 |

四个动作对照现有功能：

| 动作 | 用户的话 | 现有实现 | 状态 |
|---|---|---|---|
| **记** | 今天我要干这几件 | 今日页新建、项目文件夹 | ✅ 足 |
| **划** | 干完了，划掉 | 勾选 → 写流水（删任务也不抹历史） | ✅ 足 |
| **结** | 今天到底结了啥 | 报告卡（日 / 30天 / 半年 / 今年） | ⚠️ 有账，缺「时刻」 |
| **稽** | 你记错了，我不是这样 | 对账页（行级 ? / 日级 / 月级否决） | ✅ 最深的一块 |

**这张表就是准入标准**：新功能如果落不进「记 / 划 / 结 / 稽」，它就不属于这个产品。
四个都落不进、但用户确实要——那不是该加功能，是该做另一个产品。

---

## 3. 缺口的真正位置：它没有「时刻」

现在的界面，早上八点和晚上十一点打开，长得一模一样。

这才是「定位不清」的体感来源——**不是功能少，是它不对时间做出反应**。
一个待办清单可以没有时刻；一本账本必须有，因为账是按天结的。

| 时刻 | 用户的心事 | 界面该干什么 | 现状 |
|---|---|---|---|
| 早上第一次打开 | 今天要干几件 | 先把昨天结一句，再摆今天的空账页 | ❌ 没有 |
| 白天抬头 | 还剩几件 | 就是现在这样，越小越好 | ✅ 已对 |
| 干完一件 | 又少一件 | 立刻划掉，给「还剩 N」 | ✅ 已对 |
| 隔天回来 | 我昨天欠了多少 | 欠账摆出来，能销掉 | ⚠️ 有提示，无出口 |

只补「早上」和「销账」这两处，产品的性质就变了。**这不是加功能，是补抽象。**

## 4. 欠账：从「提示」变成「账目」

> **1.3.0 已落地。这一节保留判断过程，末尾补了实际做法和踩到的坑。**

原来的样子：`carried ≥ 2` 会挂「顺延N天」徽标（`02-plan.js:147`），
头部还有一句「3 件拖了 2 天以上」（`05-today.js:217`）。

**有提示，但没有出口。** 用户看到「3 件拖了 2 天以上」，然后呢？只能一件件去找，找到也只能勾掉或删掉。

待办软件的做法：没做完自动滚到明天，滚着滚着你就麻木了，欠多少永远看不见。
账本的做法：**这笔账滚了几天，明明白白写着，而且允许你认赔。**

要补的三件事，全部零新数据、零新权限：

```
有 3 件滚了 5 天以上
最久的一件：8 天 · 修落地页文案
[ 今天做掉 ]   [ 销账 ]
```

- **能点进去**：一句汇总 → 逐件列表，按滚的天数排序；
- **看到最久的那件**：最该被看见的不是数量，是那个你已经躲了 8 天的东西；
- **能销账**：记一笔「放弃」并写进流水。

最后一条是关键。账本允许你**认赔**：认了就不算欠，也不假装做过。
删掉是掩盖，销账是了结——这是这个产品和「列表清理」的分界线。

### 1.3.0 实际做法（含一个自己挖的坑）

做出来之后才发现：这三样东西原来全挂在 `.agenda` 里，而
`.agenda` 是 `display:none`，只有「收起态」（桌面小圆点）才 `block`。
也就是说功能写完了、断言也过了，**日常用法里一次都看不见**。

- 修：`.agenda` 在展开态也显示，但只留「要你处理」的两条（日结、欠账）；
  日期行和「还剩 N 件」在展开态是重复的，CSS 直接藏掉（`body:not(.collapsed) .a-head`）。
- 补：清单每行右侧加橙色「N天」，点它直接进欠账面板。
  在这之前，天数只有收起态和日程视图里有，而那两个地方日常不去。
- 口径：**认赔 ≠ 删掉**。原来销账走 `removeNode()`，内部记的是 `x`（删掉未完成），
  于是「我认下这件事不做了」和「这条我不想要了」在报告里长得一模一样。
  现在销账记 `q`，年轮里单独显示「认赔 N 件」。老数据不重算、不反推。
- 修：日结条的「今天已看过」原来是内存变量，一天开关三次就见三次。
  现在存进 `state.settle`，出现即算看过。

教训：**断言全绿不等于用户看得见。** 断言查的是 DOM 里有没有那个节点，
CSS 把它藏起来的时候，断言照样全过。

## 5. 与 Mole 的分界：他监控硬件，我们记账

Mole 五个模块能并列，是因为对象是**文件系统**：客观、可测、每件事都能独立做完。
我们的对象是**一个人的一天**：主观、不可测、只有一条时间线。

所以两条路必须分开走：

| | Mole | 本产品 |
|---|---|---|
| 对象 | Mac 的磁盘 / 进程 / 缓存 | 你的一天 |
| 数字性质 | 客观（CPU 就是 37%） | 主观（你说你干了 3 小时） |
| 能不能测得更准 | 能，加传感器 | **不能**，加计时器只会更假 |
| 该做什么 | 更多模块 | 更准的记账 |
| 判断标准 | 这个模块替代哪个工具 | **这一栏能不能被用户反驳** |

**结论：我们不加「更准的测量」，只加「更准的记账」。**
任何会产生「用户无法反驳的数字」的功能，都不加——哪怕它看起来很像一个功能。

这也是为什么「番茄钟 / 专注计时」封死（见 CONTRIBUTING）：它产出的 47 分钟，
无法证明、无法反驳，而且会诱导用户把它当成「我今天很努力」的证据。

## 7. 对外怎么说（三句，按场合选）

**仓库第一行**
> 一本贴在桌面上的日账本：你给自己派的活，它记着；没做完的，它算着。

**三十秒（跟体验官说）**
> 它不是任务管理器。每天把今天要干的事写在上面，干完划掉。
> 它只做一件别的待办不做的事：**没做完的会一直记着欠了几天**，不会悄悄滚到明天。
> 数据是你硬盘上的一个 JSON，断网能用，删了就没了。

**被问「和 Things / 滴答清单有什么区别」**
> 它们帮你**记住**，我帮你**算账**。它们的目标是让你别忘，我的目标是让你知道欠了多少。

## 8. 命名：为什么现在搁置，以及搁置期间的约束

卡住的原因是**先取名、后定品类**。品类定了（日账本），名字的范围会自己收窄，
那时候再挑，比现在硬凑容易得多。

搁置期间守三条，否则以后改名要掉权限、掉数据：

1. **bundle id 不许再动。** `local.desktodo.app` 已经是权限（日历/提醒/磁盘）和数据路径的锚点，
   改一次掉一次授权。
2. **名字只有 13 处、7 个文件**（`grep -rn "浮窗待办" src/`），改名是机械活。
   真正贵的是 bundle id，不是文案。
3. **工作名不进定位句。** 「浮窗待办」继续当工作名用，但对外第一句必须说品类，
   不说名字——否则每换一次名，对外认知就重建一次。
